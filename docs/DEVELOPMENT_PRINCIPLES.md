# PathoReason 通用开发与能力验证规则

生效日期：2026-10-31。适用于本项目的功能开发、运行监控、故障排查、运行时/基模适配、Skill 与工具维护及阶段验收。不限于某个 session、模型、病种或当前研究项目。用户对具体任务的明确指令优先；历史阶段记录保留其原有证据范围。

## 目标与职责

开发工作的目标是让系统在真实条件下稳定完成用户任务。真实研究暴露的问题，应转化为可复用的系统能力和可核验的回归证据。

开发助手负责运行时、配置、提示词、上下文、工具、Skill、业务接口、状态与恢复机制。研究 Agent 负责在用户授权范围内调用这些能力，完成数据处理、分析、报告和成果登记。科学判断、作者审核和训练授权继续按独立门禁执行。

开发监控可以只读检查研究输入、调用轨迹、原始输出和账本，以确定问题；不能为让本次任务看起来成功，直接修改研究 Agent 的项目脚本、数据集、统计结果、报告或已登记成果。开发者完成的结果不是系统自主完成的证据。

用户若明确另行要求修复某份研究材料，可以按该具体范围执行；保留原版本，标明操作者、修订理由和来源，并将人工修复与模型验收结论分开。这不是开展常规系统修复前必须新增的审批流程。

## 从真实失败改进能力

1. **保留失败现场。** 记录任务要求、实际授权、模型与运行时版本、配置、预算、关键调用、错误和已产生文件。区分进程退出、工具成功、回合完成、研究任务完成及科学审核通过。先确认运行状态，未知执行结果先核对，不盲目重发。
2. **定位责任层。** 判断是运行上限或配置、协议适配、工具实现、上下文不足、数据契约、模型执行策略、权限/预算，还是输入本身缺失。不要把所有问题归结为模型能力，也不要用提高预算掩盖死循环或工具缺陷。
3. **修复合适的公共层。** 可重复的确定性操作进入工具或 helper；领域流程与判断规则进入 Skill；模型/引擎差异进入适配层；状态丢失或重放风险进入持久化与恢复机制。只保留有证据支持的规则，避免把每次失败都变成全局限制。
4. **构造有代表性的回归。** 使用最小夹具或隔离验收目录复现失败条件，验证实际行为和边界。不要把当前病种、患者数、文件路径或期望研究结论写死成系统答案。凭据和患者明细不进入通用 Skill、测试样例或源码。
5. **由系统重新证明能力。** 工程修复通过后，在已有授权及明确预算内由目标运行时和基模调用新能力；尽量保持任务、输入和评价口径可比，记录变化项、失败、消耗和人工干预。不能由开发助手代做输出来通过验收，也不能悄悄重置失败预算。
6. **保留可追溯交接。** 提交公共源代码、配置、规则及必要文档，记录部署与回退方法；运行证据放独立数据盘目录。交接说明已验证范围、未验证行为和下一项可观察指标。

这些步骤按任务复杂度执行。小型配置或文档修订采用相称的检查，不要求所有改动都新建流程、请求审批或重复跑全量测试。

## 运行限制与权限

步数、超时、上下文大小、输出长度、并发和重试次数都是可调工程参数。判断合理性应结合：是否仍有实质进展、在哪个阶段中止、完成率、工具失败/重复次数、延迟、token/费用及项目剩余预算。

有进展却频繁被截断时，可以在用户授权范围内提高有界上限并观察后续行为；反复空转时，应优先修复策略、工具或上下文。不能将某个当前值固化为永久正确值，也不能默认取消所有限制。模型迭代步数、应用回合数、累计墙钟、GPU/训练时间和付费图像额度分别记录，不混用。

同一范围已经授权的工作可跨回合继续，不机械重复申请。原生工具权限按当前会话设置执行；允许工具调用不等于扩大研究范围、增加预算或绕过科学/作者门禁。未经授权的范围扩张仍按具体任务处理。

## Skill 与工具设计

- Skill 描述何时使用、关键协议、关联关系、来源要求、失败恢复和交付边界；保持能跨项目复用。接口细节放参考文件，机械分页、校验和回执保存优先由可测试 helper 执行。
- Skill 必须被目标引擎发现并可实际调用，必要时接入产品目录和可信提示词。文件存在、目录注册、模型实际加载、任务行为正确是不同证据。
- 不把某次错误对应的具体答案写进 Skill，也不堆积与任务无关的警告。规则应帮助 Agent 正确执行，而非让开发者代替 Agent 执行。
- helper 保持输入、输出、失败语义和副作用边界明确。原始证据、派生结果和完成回执分开；中断后的恢复以真实回执为依据，不以 Agent 的文字推断完成。
- 支持研究 Agent 检查自身输出、发现异常、产生新修订及登记成果；这些动作仍由受测系统在真实任务中完成并记录。

## 验收证据与报告

| 验证层级 | 可以证明 | 不能据此声称 |
|---|---|---|
| 静态/单元/夹具测试 | 契约、确定性逻辑、已覆盖的错误边界 | 真实基模已正确执行任务 |
| 原生集成检查 | 配置生效、Skill 可发现、协议与权限可用 | 模型已选对工具或完成研究 |
| 目标引擎＋基模行为验证 | 在记录的任务、输入和预算内实际调用并产生结果 | 其他病种、模型或范围都通过 |
| 研究与科学审核 | 对应研究结论及门禁的实际审核结果 | 仅凭工具成功自动通过全部审核 |

每次适配修复至少说明：观察到的失败、根因证据、公共层改动、实际验证方式、结果与剩余限制。真实行为验证记录还应标明引擎/模型、Skill/配置版本、输入来源、独立预算及消耗、关键调用、输出归属和人工干预。

未开展目标模型行为验证时，明确标为“工程/集成检查通过，模型行为待验证”。开发者人工修正后的结果必须保留独立来源；不能计入模型自主完成率或覆盖失败记录。对已有任务的只读诊断可作为问题证据，但不能充当修复后的行为验收。

## 例子

- Agent 到达步数上限但仍在正常推进：分析步骤和剩余预算，调整运行配置，再观察目标 Agent 的收尾能力。
- Agent 反复写错接口分页或跨表关联：沉淀协议 Skill 和通用 helper，加入分页、范围、来源与恢复回归，让 Agent 自己调用并核验结果。
- Agent 生成了错误统计或报告：保留原结果和失败证据，修复可复用的工具/指导/检查能力；不在开发监控中直接替它改成正确答案。
- 平台出现权限派发、状态同步或恢复缺陷：修复平台机制并验证不重复执行；不靠直接改研究账本将任务标记为成功。

## 自然语言交互验收

交互目标及按钮引导遵循 [design.md 的任务推进规范](../design.md#以推进任务节点为目标的交互)。验收以有效任务节点的推进为依据：关键选择是否解除障碍、点击与等价自然语言是否一致、是否重复确认、过期选项及重复操作是否被正确处理。不能用界面显示成功或模型回合完成代替实际任务状态变化；文档提出设计要求不代表控件已实现。

系统应在日常短句下工作，不能把用户能写完整技术提示词作为能力前提。按上下文绑定最近提议、已有方案、授权和执行状态；可逆且目标明确的修改继承未变参数并交付新版本，必要默认值简短说明。仅对会实质改变行动的缺口提出聚焦问题，不反复要求确认已接受的唯一方案。存在多个未选择选项时不能替用户虚构选择；模糊推进不扩大数据、计算预算或冻结测试边界。

交互回归必须覆盖默认推进、唯一提议后的短确认、多选项澄清、执行意图和范围边界。向受测模型提供实际短句和真实或明确标记的合成上下文，不注入期望答案或隐藏的完整请求。检查实际工具行为、成果、授权与原文件变化，不只评最终措辞；保留原始回复及人工工具审批。合成上下文附带的上文与真实多轮会话分别记录，工程通过不能替代模型行为验收。


## 目标推进与自主执行

用户委托的是目标，不是固定次数的回复。公共平台应持久化目标、验收条件、范围、预算、节点和阻塞，并在实际回执显示下一项已就绪时自动接续。系统续行须记录系统来源，不伪造用户指令、选择或授权。一次模型回复结束不等于目标完成；自报完成、关联材料可核验、科学审核通过必须区分。

停顿应对应完成、需要用户决定、能力缺口、失败、预算或用户暂停/取消等可解释原因。常规步骤不要求用户反复发送“继续”。未知派发先核对，重复无进展有界停止；用户修订和恢复不得删除失败或重置预算。上下文压缩后仍由持久目标恢复事实，不能靠摘要扩展授权。用实际目标引擎与基模验证跨回合行为；开发者不修改其研究输出来实现目标。当前实现及限制见 [目标推进](p5/GOAL_CONTROL.md)。
