## 日常运行与备份

当前账号 crontab 每分钟运行 `scripts/delivery_watchdog.py`，只启动身份核对后缺失的本部署服务；重启主机后也会执行。每晚服务器时间 03:15（CST / UTC+8）执行 `scripts/backup_delivery.py`。监护与备份日志位于 `runtime/control/delivery-watchdog.log`、`delivery-backup.log`。

备份位于 `/data/bxn/PathoReason-delivery-backups/nightly/`。SQLite 一致性备份、所有关联目录、原生数据库副本和登记成果 SHA 检查完成后才写 `complete.json`；研究活动中或复制期间平台发生变化则保留不完整目录并报错，不冒称成功。未变化的备份文件仅在不同备份之间使用硬链接，绝不与在线数据硬链接。没有自动删除历史备份的规则，应按磁盘容量安排后续留存策略。

维护前先创建 `/data/bxn/PathoReason/runtime/control/delivery-maintenance`，暂停监护自动启动。核对平台回合、目标、原生会话、训练、权限派发均无未决执行，再执行 `scripts/service.py stop-app`。正常上线后检查服务与数据，再移除维护标记。停止应用不代表训练停止，不对运行中的科研任务直接发布。

## 发布后续版本

1. 开发目录完成变更、合适的工程/集成验收与提交；真实模型验证另遵循已批准范围与预算。
2. 在开发环境准备候选发布包和独立前端构建，记录提交、锁文件及 SHA；不要让开发构建覆盖交付 assets。
3. 确认空闲、保存当前一致性备份、设置维护标记后，将通过验收的提交发布到交付分支。同步对应构建和经审阅的配置变更，涉及数据库结构变化先验证迁移兼容性。
4. 启动交付应用，验证 Tailscale 地址、案例、对话、稿件/图表下载和关键接口，生成新的交付标签，再移除维护标记。

回退优先恢复兼容代码和前端，不得用旧数据库覆盖甲方使用后产生的新数据。恢复完整数据快照属于单独的灾难恢复操作，须审阅差异及原生状态，不能直接运行备份中的旧 PID 控制文件。Git 推送仍通过已登录的本机 HTTPS 中转，服务器没有新增 GitHub 凭据。
