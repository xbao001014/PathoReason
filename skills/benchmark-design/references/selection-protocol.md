# 选型与比较规则

## 候选方法应回答的问题

- 该方法为何能检验当前论文的主张？是经典锚点、近期强参照、不同建模路线，还是简单 sanity baseline？
- 论文的任务/数据/训练设定与当前项目有何差异？只报告他人论文的性能不能用于当前数据上的模型排名。
- 是否支持当前已有特征维度、bag 大小、多切片患者聚合和标签粒度？需要坐标、图结构、额外模态、预训练权重或重新提取特征时单列。
- 官方实现是否可定位？记录 URL、版本/commit（已核实时）、许可及依赖。暂未核验写 unknown，不猜成 MIT 或“可直接运行”。
- 库内实现与论文原方法是否一致？可能只是同名变体；需记录来源和差异。
- 若排除，理由是任务不适合、输入不足、证据不足、资源代价，还是执行器暂未接入？最后一种是工程缺口，不是科学上的不值得比较。

候选覆盖由研究问题决定，不强制所有项目使用同一组模型。应有合适的经典参照与近期相关强方法，并解释技术路线覆盖。不要为了凑数量纳入重复变体；不要只保留容易击败的旧模型。若近期方法均不适用，应给出实际检索和逐项理由，不能以空候选表代替检索。

## 比较公平性

- 固定特征轨：编码器、特征版本、患者划分、训练/验证/测试身份一致；比较聚合器时说明输入维度适配。模型原方法确需坐标或不同 bag 处理时说明差异与影响。
- 编码器或端到端轨：明确新增数据、预训练、特征提取和计算成本；与固定特征轨分开呈现，避免把收益全部归因于聚合器。
- 相同资源不必机械等于相同超参数。采用有依据且成本可比的调参规则、模型适用配置、统一选择准则；不得给拟议新方法更大的搜索预算而不说明。
- 患者级任务保证患者不跨集合；多切片患者如何产生一个预测应预先写清。CV、验证集和最终封存测试的职责互斥，不能将 CV 内测试和最终测试混称“只测试一次”。
- 从模型数、设置数、折数、种子和独立最终拟合规则计算运行总数。smoke、CV、最终训练/推理、敏感性分析分别计数；锁定测试不能用于继续选模型/超参。
- 资源估计应有来源或明确为待测估计；需要性能 smoke 时另走授权的计算步骤，不以计划阶段直接启动训练估时。

## 常见链路错误

“sealed runner 只支持两种模型，所以论文只比较两种” → 先列科学上应比较的方法，再列 runner 适配缺口及实施顺序。

“两个模型各两种 patch 数就是四个 baseline” → 两种模型、两种采样设置；后者作为敏感性或统一预算条件。

“仓库存在 configs/modules/process，因此 trainable” → 仅 structural_complete；还需输入适配、依赖、执行器、隔离和预算门禁证据。

“本次检索没有发现新方法，所以不存在” → 记录查询与覆盖局限，扩展同任务/相邻领域或其他学术索引。

## 输入需求的证据

将缺额外输入作为暂缓或排除理由前，核对原论文的方法/数据说明或官方 forward/数据加载接口，写出具体来源位置。不要仅凭模型名、Transformer/位置编码等术语推断必须有绝对坐标、原始像素或额外标注。区分原论文硬要求、可选增强、现有实现限制与尚未核验的猜测。

样本数不能整除折数时，显式记录各折 OOF 人数并核对总和等于开发集人数；不要把整数近似写成每折精确相同人数。内部 train/validation 的人数也需按实际该折剩余样本计算。计划中的 split_counts 是人数核对，不替代后续真实患者 ID 不交叉/全覆盖检查。
