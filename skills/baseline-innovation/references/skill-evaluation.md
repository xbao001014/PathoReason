# 后续效果验证协议

本文件是待执行的验证设计，不是已获预算的实验，也不是研究结果。目标是判断三个 Skill 是否改善当前基线之后的创新质量和执行闭环，而非让开发助手代替研究 Agent 产出成功答案。

## 固定比较条件

由研究 Agent/平台在授权范围内冻结同一输入包：用户目标、基线选择依据、数据/特征与主体划分、主指标、代码/环境版本、基线原始结果、既有失败/测试暴露、现有候选、可用工具和权限。保留内容哈希与来源；分支之间不得泄漏新增候选或结果。若保留历史候选，两组都提供并说明是在评价改进而非从零构思。

记录 OpenCode/模型/Skill 版本和实际加载轨迹。两组使用可比的 Agent 额度及独立训练预算上限，实际消耗另记，未知费用不填零。新验证不能重置原项目账本；建立独立、有来源的验证分支/会话与预算须沿用平台机制及用户授权。历史报告可以作为参照，但旧会话与新会话的直接差异不是受控因果证据。

## 分阶段验证

1. **静态/工程**：frontmatter、相对链接、候选字段兼容、现有工具与权限边界。此层无需模型或训练。
2. **原生集成**：只读核对注册路径与 native Skill 清单；后续真实回合核对实际加载正文/哈希。看见目录不等于模型使用；不为验证重启活动进程。
3. **模型行为**：同冻结输入下比较“现有工作流、未加载新增 Skill”与“新增三 Skill 工作流”。确认对照没有意外加载新 Skill；否则标为污染，不算干净对照。先只生成方案和准备材料，均不训练。保留原始调用、阻塞、人工干预和预算；重复次数由用户预算决定。单次配对是试点，不能证明稳定提升。若总效果值得继续，才考虑逐项消融，避免预先扩大实验规模。
4. **科学实验**：用户选定方向并批准具体独立训练预算后，才按公共执行器比较候选与冻结基线。先使用开发/验证数据，最终评估依协议；当前已曝光测试的结果明确非独立、非盲法，不以新实验名消除偏倚。它能检验本地改善，但不能单独证明未见数据泛化或论文原创性。

## 在看新方案前固定评审表

每项记录 0=缺失/错误、1=部分具备、2=有可核验依据；这是本项目试点评审尺度，不是论文验证过的量表。分别报告，避免总分掩盖严重问题。

- 基线锚定：依据验证表现、稳定性、代价，保持用户选择；已知测试选择偏倚明确。
- 文献与差异：来源真实、与实际读取内容一致，最相近工作和实质差异可核验。
- 机制与证据：区分事实和假设，适配现有输入，给出反例/替代解释。
- 判别设计：对照、消融、机制读数和无效/不确定标准足以检验假设。
- 执行可行性：可映射到当前源码、环境、受控输入和公共执行器；成本有依据。
- 连贯推进：关键选择后继续，不重复冻结确认；恢复状态正确，阻塞有明确解除节点。

严重失败单列：伪造来源或结果、开发测试泄漏、未授权训练/加额、绕过执行器、删除失败或消耗。完成数不能抵消这些问题。

若有授权的独立评审者，可隐藏分组身份、随机材料顺序，并记录分歧；开发助手自评必须标为非盲法。候选数量、字数、运行时长及 GPU 利用率不是创新质量替代指标。

真实实验报告包含预定主指标相对匹配基线的差值、跨种子/折波动、机制消融、成本、失败与暴露记录；多个候选的选择过程和多重比较限制必须保留。分别给出工程、原生、模型行为、科学结论。一次有效改进也不能独自归因于 Skill：需结合可比对照及重复证据。

## 适合后续试点的自然语言入口

“围绕当前结果较好的基线提出创新方案，先核对基线选择和原始证据，加载 baseline-innovation；给出可证伪的机制与最小对照，暂不训练。”

用户选定方向后，innovation-experiments 负责自主准备到可审阅方案；训练终态或恢复时由 innovation-checkpoint 复盘下一节点。这些提示用于发起后续验证，本次创建 Skill 不执行它们。
